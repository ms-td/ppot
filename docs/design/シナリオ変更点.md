# シナリオ変更点 (分析-クラス指定 → 設計-クラス指定)

設計フェーズにはまだシナリオを書き写す図 (コミュニケーション図 / シーケンス図) が無いので、
分析モデル `分析-クラス指定` のシナリオ
([communication-scenarios-クラス指定.md](../analysis-analog/communication-scenarios-クラス指定.md))
を元に、設計モデルの変更で書き換わる箇所と、追加が必要なシナリオを列挙する。
手順番号は分析側の各シナリオ「基本」のもの。

変更の出どころは次の 3 つ。

- **方針変更**: 保温中のモード変更は再沸騰させず、保温中のまま目標温度を変える (2026-11 講師指示。§1)
- **構造変更**: 設計モデルでのインターフェイス / Observer / テンプレートメソッドの導入 (§0)
- **抜け**: 分析時点から書かれていなかった要求 (§3)

## 1. 方針変更: 保温中のモード変更は保温中のまま追従させる

### 変わること

sheet3 の「保温モードに設定した際に100°Cでなかった場合、一度沸騰させたあと、自然に冷ましながら
設定温度に保つ」は採らない。保温行為中にモードが変わったら、保温行為中のまま
**新しい保温温度を目標温度として各所に配る**。沸騰行為中 / アイドル中の変更は、
これまで通り次に保温行為へ入ったとき 保温温度 を読むだけでよい。

### 決着: 保温モード を Subject とする Observer (モデル反映済み)

- `IKeepWarmModeListener` の操作は `モード変化(モード: enum 保温モード)` (`notifyModeChanged`)。
  旧 `モード表示変更` を改名したもの。
- 実現するのは 表示部 と 保温行為 の 2 つ。保温モード が `1..*` の
  `リスナ` (`m_listeners`) として持ち、`リスナ登録` (`addListener`) で登録する。登録解除は無い。
- 渡すのは enum だけにする。enum 保温モード のメンバーは値として温度 (98 / 90 / 60) を持つので、
  enum を受け取るリスナはそこから温度もわかる。モードと温度を両方渡す必要はない。
- 温度エラー監視 へは、保温行為 が `目標温度変更(目標温度)` (`changeTargetTemp`) で渡す。
  呼ぶ経路は、基底 温度制御行為 から継承している関連 (`m_tempErrorMonitor`) を使う。
  判定側へは、既にある `温度エラー確認(目標温度, 経過時間)` の引数で毎回渡る。
- `監視開始` を呼び直さないので、判定のリセットは起きない。
- 保温行為へ入るときは、これまで通り 保温行為 が 保温モード から `保温温度読み出し` で読む
  (関連 2348 は残してある)。監視開始の目標温度にもその値を渡す。
- 温度エラー監視 を直接 Observer にする案は、いったんモデルに入れてから取り下げた。
  モード変化は 沸騰行為中 / アイドル中 にも届くので、沸騰中の目標温度 100°C を上書きしないよう
  「いま保温を監視中か」を 温度エラー監視 が判断することになる。保温中かどうかを元から知っているのは
  保温行為 なので、そこから渡すほうが判断が増えない。
  `監視開始` に「目標温度を固定する」bool を足す案もあったが、ややこしくなるので採らない。

### 「保温モードボタン押下から保温モードが変更されるまで」の書き換え

手順 1〜9 (ボタン → 操作部 → リスナ(ポット) → 蓋の閉確認 → 単発鳴動 → 保温設定変更) は
§0 の書き換え以外そのまま。末尾のコメント 4 行 (保温行為中か → 現在水温 →
100°C 未満なら給湯停止 + 沸騰要求) は**丸ごと削除**する。10 以降は次に置き換える。

```
10. 保温モードはリスナへ上記で変更したモードでモード変化を通知する
    // リスナは 表示部, 保温行為 (順不同)
11. 表示部はモード表示へ表示を指示する [pot-240-41]
12. 保温行為は保温中ならば, 目標温度をモードの保温温度にする [pot-240-31, pot-320-21]
    // 保温中でなければ何もしない (次の開始時に保温温度を読む)
13. 保温行為は保温中ならば, 温度エラー監視へモードの保温温度で目標温度変更を指示する [pot-500-31]
    // 判定はリセットしない. 沸騰行為中 / アイドル中は 12 と同じく何もしないので, 沸騰中の 100°C は上書きされない
// 以後、PID は新しい目標温度に向かって操作量を出す. 上げるときは加熱, 下げるときは操作量0%で自然に冷める.
```

### 気をつけること

- 保温モード の属性 `保温温度` (`m_iKeepWarmTemp`) は、enum の値と同じものを二重に持つ形になる。
  `保温温度読み出し` の戻り値のためだけに残すかは、後で整理してよい。

### 残っている確認: pot-500-21 の 3 分の数え始め

文言は「保温の各モードに**なって**3分以上」。

- モード変更でリセットすると、文言には忠実になる。しかし、3 分以内にボタンを押し続ければ
  温度下がらずエラーを出させないことができてしまう。
- これまでは、リセットする経路が必ず カルキ抜き (3 分間の加熱継続) を通り、その間は
  pot-500-11 (110°C) が見張っているので問題ない、と整理していた。
  今回の方針ではモード変更が カルキ抜き を通らないので、この理屈が成り立たない。
- 判定の閾値 98°C はモードによらないので、**保温行為への入場時だけリセットし、
  モード変更ではリセットしない**ほうが安全側。こちらの見解はこれで一致している。講師に確認する。
- 講師の答えがどちらでも構造は変わらない。リセットすることになったら、温度エラー監視 の
  `目標温度変更` の中で 温度下がらず判定 の `リセット` を呼ぶだけ。

### モデル側に連動したもの

- `行為切替.現在水温読み出し` / `温度制御行為.現在水温読み出し`: 削除済み。
  呼び手は再沸騰判定だけで、各行為や判定はサーミスタを直接読んでいる。
- 保温行為 の状態遷移図: 保温中 に「モード変化」の内部遷移 (または自己遷移) が増える。
- 保温中に目標温度が変わっても、PID は増分形なので内部の前回値はそのまま使ってよい
  (目標の段差は Ki(Tg−T0) の項に効くだけ)。

## 5. 能動クラス (Is Active) とシナリオの「待ち / 定期」

分析シナリオの「(3sec後)」「(100msec後)」「定期で更新する」「(3分経過後)」は、設計では
`loop()` で回されるクラスの中に入る。いま Is Active にしてあるのは次の 9 つ。

- インジケータセル (点滅)
- ブザー (鳴動時間・回数)
- ボタン (100ms 受け入れ)
- 蓋 (閉 3 秒 / 開 1 秒の確定、pot-220-11, 221-11)
- 温度エラー監視 (1 分周期)
- 温度制御行為・沸騰行為・保温行為 (制御周期、カルキ抜き 3 分)
- 水位計 (センサ読み取り)

整理済みのもの:

- ポンプ は作動 / 停止の指示を受けるだけなので、能動ではない (Is Active を外した)。
- 温度制御行為 は能動で、派生の 沸騰行為 / 保温行為 はその性質を引き継ぐので、3 つとも指定してある。
  `loop()` は派生側で実装する。
