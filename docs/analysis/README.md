# 分析モデル (話題沸騰ポット GOMA-1015型)

`docs/spec/` の要求仕様から作成した**分析モデル**を置く. 図は PlantUML で記述し, 同名の
PNG を隣に生成する.

## 分析モデルと設計モデルの位置づけ

| | 入力 | 読み手 | 目的 |
|---|---|---|---|
| **分析モデル** (このディレクトリ) | 要求仕様 (`docs/spec/`) | 人間 (仕様の理解・レビュー) | 要求仕様に何が書かれているかを図で説明する |
| **設計モデル** (今後 `docs/design/` を想定) | 分析モデル | 実装作業者 | 実装の指針を与える |

分析モデルは**要求仕様に書かれていること以上を決めない**. 実装上の判断 (クラス分割の粒度,
言語, データ構造, タスク分割など) は設計モデル側の仕事とする. そのため分析モデルの図は
**日本語のみ**で記述し, 要求仕様の用語をそのまま使う (英数字は要求IDと単位のみ).

### package = 機能

package はハードウェアの分類ではなく**機能**で切る. 根拠は, 正典である sheet4 自身が

B2:  ＜構成要素と動作モード＞   pot-210 コンセント / pot-220,221 蓋 / pot-230 沸騰ボタン / pot-240 保温モード

B157:＜温度制御方式＞         pot-400
B186:＜エラー検知＞           pot-500

### 複数の機能から使われるオブジェクトの所属規則

PlantUML の package は重複できない. 一方, 複数の機能から使われるオブジェクトが存在する.

| オブジェクト | 使う機能 |
|---|---|
| 蓋センサ `pot-110-15` | 蓋判定 `pot-220-11`/`pot-221-11`, 水位判定のタイミング `pot-280-11`/`-12`, モード切替条件 `pot-240-21`, ロック操作条件 `pot-250-21`/`-31`, 給湯条件 `pot-260-11`, 温度制御停止 `pot-310-31`/`pot-320-31` |
| 第n水位センサ `pot-110-13` | 水位判定 `pot-280`, 温度制御停止 `pot-310-31`/`pot-320-31`, 給湯条件 `pot-260-11` |
| サーミスタ `pot-110-16` | 温度制御 `pot-400`, カルキ抜き `pot-311-11`, エラー検出 `pot-500-*` |
| ヒータ用電源 `pot-110-18` | 給湯条件 `pot-260-11`/`-21`, エラー処置 `pot-500-*` |
| ブザー `pot-110-22` | ボタン受付 `pot-230-11`/`pot-240-21`, エラー `pot-500-*` |

**規則: その値を決める (書き込む) 機能が持ち, 読むだけの機能は破線で参照する.**

- 蓋センサ → 値は物理の蓋が決めるので **2.蓋の開閉**. 3/4/5 が条件として参照する
- 満水センサ・第n水位センサ → **3.水位**. 4/5 が参照する
- サーミスタ → **4.温度制御**. 6 が参照する
- ヒータ用電源 → off にするのはエラー処置だけなので **6.エラー**. 4/5 が参照する
- ブザー → 3つの機能から鳴らされ単独のオーナーがいないので **1.ポット全体**

副次的な効果として, **蓋センサが多数の機能から参照されるハブであること**が図から読み取れる.
これはこの系で最も影響範囲の広いセンサなので, 分析結果として意味がある.

失うものもある. 物理的な取り付け関係 (貯水部にセンサが付く, 蓋にパネルがはまる) が package
では表せなくなるため, 貯水部と操作パネルには `取り付け部品` / `配置部品` という属性を持たせて
補っている.

### 属性値の根拠注記

すべての属性値の末尾に**根拠**を付ける. これが「人間向け説明図」の核になる.

| 記法 | 意味 |
|---|---|
| `【pot-280-41】` | 要求仕様でその値が決まっている. IDは `docs/spec/要求仕様.txt` / `ハードウエア構成とハードウエア要求仕様.txt` を grep すれば引ける |
| `【シーン仮定】` | 仕様では決まっておらず, このシーンを描くために置いた値 (水温の実測値, ボタンの押下状態など) |
| `【仕様未定義】` | 仕様書に記述がない項目 (制御周期, Kp/Ki/Kd, ブザー周波数, エラー時の表示) |

推論が混ざる場合は併記する
(例: `検出値 = off 【シーン仮定: 給水線まで注水】【pot-110-19: 給水線は満水センサより若干下】`).

線種:

- **実線 `―`** … 構造的な関連 (所有 / 取り付け)
- **破線 `..>`** … 参照 / 指示 / 条件

各図では**直前の図から変化した値を `<b>太字</b>`** にしている.

### モデル化にあたっての判断

- **満水センサは第n水位センサ配列の n+1 番目としてモデル化しない.**
  `pot-280` の説明に「満水を判断するセンサーだけは他のセンサーでは代用できないので, 別な機能と
  位置づける」とあるため, 別の概念クラスとする.
- **ヒータ と ヒータ用電源 は別オブジェクト.** `pot-110-18` の説明に「電力供給状態≠ヒータ
  動作中. ヒータon=ヒータ動作中」とある. `pot-500-*` が off にするのは**ヒータ用電源**であって
  ヒータの操作量ではない. 図04はこの分離が効いている例で, ヒータが止められない故障でも
  電源を切れば加熱は物理的に止まる.
- **温度制御行為は「現在存在する行為オブジェクト」で表す.** 図01はアイドル, 図02は沸騰行為,
  図03は保温行為, 図04はエラーのオブジェクトが存在する. シーンによってオブジェクトの個数と
  種類が変わることで, オブジェクト図としての意味が出る.
- **インジケータセルは4個の実体を描くが, クラス図での多重度は `1..*` とする.**
  `pot-120-11`「水位センサと同数」, `pot-280` 説明「コストダウンによって数が変動する可能性」.
- **モデル化の対象外**
  - キッチンタイマ (タイマボタン, タイマ残り時間表示窓) … sheet3 の操作パネル表にのみ存在し,
    sheet4 に対応する `pot-NNN` 要求が存在しない
  - 取手 `pot-100-14`, 水路 `pot-110-21` … 制御に関与しない受動部品
  - ブザーの鳴動元のうち `pot-230-11` (沸騰ボタン 100msec) と `pot-240-21` (保温設定ボタン
    100msec) は**未反映**. 「要決着」の項を参照

## 「満水」の解釈

要求仕様において**満水センサ on は「水量が適正」ではなく「異常」**である.

- `pot-110-11` 満水センサ on = 水位が**許容上限を超えている**
- `pot-280-11` 蓋センサ on から 3sec 経過時に満水センサ on → 許容上限超えと判断 = 水量異常
- `pot-220-31` 水量が異常な場合, 蓋が閉じられても状態は**アイドルのまま** (沸騰しない)
- `pot-110-19` 給水線は満水センサの位置より**若干下**

したがって「水を入れて蓋を閉めたら沸騰が始まる」状態は**給水線まで**入れた状態
(満水センサ off, 第1〜第4水位センサすべて on, 水位メータ 4 セル全点灯) である.
図02はこの解釈で描いている.

## 決着済みの判断

### 1. 満水センサ on を温度制御停止条件に含める

仕様書内で記述が食い違っていた.

| 出典 | 温度制御停止の条件 |
|---|---|
| 状態遷移シート 7章 イベント表 (`images/image15.png`) | 蓋センサ off, 全水位センサ off, **満水センサ on** |
| sheet3 `B149` | 「第n位センサーON」かつ「満水センサがOFF」の場合のみ沸騰ボタン・ヒーターが動作 |
| sheet4 `pot-310-31` / `pot-320-31` / `pot-330-12` / `pot-330-13` | エラー検知, 蓋センサ off, 全水位センサ off の**3つのみ** |

**決定: 満水センサ on を温度制御停止条件に含める** (状態遷移シートと sheet3 に従う).
満水センサは異常を示す要素としての性格が強く, `pot-110-12` がデフォルトを on (故障時は
安全側) と定めているのと整合するため.

補足として, 実際の運用では**この条件が単独で効く場面はほとんどない**. 物理的に水を足すには
蓋を開ける必要があり, 蓋センサが 1sec 以上 off になった時点で `pot-221-11` により温度制御行為が
先に中止されるからである. その後蓋を閉じれば `pot-220-11`→`pot-280-11` の経路で満水が判定され,
`pot-220-31` によりアイドルのままとなる. したがってこの条件が意味を持つのは,
満水センサの故障や, 沸騰による水面の変動といったケースである.

### 2. sheet3 の安全性要求 vs `pot-500-*` → sheet4 を正とする

sheet3 の `安全性要求` (行137〜146) は 100°C / 5°C / エラー2種と書くが, sheet4 の
`pot-500-11` / `-21` / `-31` は **110°C / 8°C / エラー3種** (温度下がらずエラーを含む).
**sheet4 (`pot-500-*`) を正**とする (`CLAUDE.md` の指示と一致).

### 3. ランプの点灯条件 → `pot-310-11` / `pot-320-11` / `pot-330-41` を正とする

sheet3 `C98`「沸騰中以外点灯」に対し, `pot-330-41` はアイドル時に沸騰ランプ・保温ランプを
**ともに消灯**とする. sheet3 の `B151`「ヒーターが動作していない場合, 沸騰ランプと保温ランプは
消灯」は sheet4 と一致するため, sheet4 側を採用する.

### 4. 未定義の数値は設計モデリング時に決める

以下は分析モデルでは**【仕様未定義】のまま扱う**. 設計モデリングの段階で決めればよい.

- 制御周期の値 (`pot-400-11`, `pot-400-31`)
- PID 係数 Kp / Ki / Kd の値 (`pot-400-31`, 「水の温度特性により決定される」とのみ)
- ブザーの鳴動周波数 (`pot-110-22`, `○○KHz` のまま)

### 5. 欠番はキッチンタイマの要求群

`pot-270` および `pot-330-31` の欠番は, 元はキッチンタイマの要求群だった箇所である.
今回のモデリングではキッチンタイマを対象外としているため, 欠落したままでよい.

### 6. package はハードウェア分類ではなく機能で切る

当初は「外観 / ハードウェア境界 / 操作パネル部品 / 制御」という区分だったが, 前3つが物理分類で
最後だけが機能分類という**軸の混在**になっていた. sheet4 自身が機能で構成されていることを
根拠に, 6つの機能 package に切り直した. 詳細は「図の読み方」を参照.

## 要決着の項目

### A. `pot-500-21` が自然冷却中に成立してしまう

`pot-500-21` の文言は「保温の各モードになって**3分以上**水温が **98°C を超えていた**場合,
ヒータ用電源を off して 30秒間ブザーを鳴らす」である. しかし:

- 沸騰行為は 100°C まで加熱してカルキ抜きを 3分行う (`pot-311-11`)
- その後 `pot-312-11` で保温行為に移る
- sheet3 `B152` は「保温モードに設定した際に 100°C でなかった場合, 一度沸騰させたあと,
  **自然に冷ましながら**設定温度に保つ」とする
- 貯水部は「断熱性の高いステンレス素材」(`pot-100-15`) なので, 100°C から 98°C を割るまでに
  3分以上かかることは十分ありうる. 特に節約モード (90°C) やミルクモード (60°C) では
  自然冷却の時間が長い

つまり**正常な冷却中に温度下がらずエラーが誤検知される**. 解釈の候補:

1. `pot-500-31` と同じく「**ヒータ制御中**に」の限定を補う (操作量 M > 0 のときだけ判定する)
2. 3分の計測開始を「保温の各モードになって」ではなく「**目標温度に到達してから**」とする
3. 判定温度 98°C をモードごとの目標温度に連動させる

### B. エラー時の表示が規定されていない

`pot-500-*` はヒータ用電源の遮断とブザー鳴動しか規定しておらず, **表示について何も言わない**.
図04では以下が【仕様未定義】になった.

| 出力 | 図04で置いた推定値 | 推定の根拠 |
|---|---|---|
| 沸騰ランプ / 保温ランプ | ともに消灯 | sheet3 `B151`「ヒーターが動作していない場合, 沸騰ランプと保温ランプは消灯」 |
| 温度/モード表示窓 (温度) | 表示を継続 (99) | `pot-330-42` はアイドル時のみ非表示を規定. エラー時は未規定 |
| 水位メータ / インジケータセル | 通常表示のまま | `pot-221-12` は蓋開時の全消灯のみ規定 |
| 保温設定ボタン / 解除ボタン の有効性 | 未定 | `pot-240-21`・`pot-250-31` はエラー時に言及しない. 一方 状態遷移シート 6.2 はエラーを全イベント無視のトラップ状態とする |

### C. `pot-500-31` の 8°C の境界

`pot-500-31`「目標温度よりも水温が **8°C下がり**」は境界を書いていない. ミルクモード (60°C) の
とき, 52°C ちょうどが該当するのかしないのかが決まらない. 同じ `pot-500` 群でも `pot-500-11` は
「110°C を**超えた**場合」と明示しており, 書き分けが不統一である. 図では
「目標温度より 8°C 低い (60→52°C)」と書き, 境界の扱いは【仕様未定義】と注記している.

### D. ブザーの鳴動元

sheet4 に明記されている鳴動元は次の3つ.

| 主体 | 鳴動 | ID |
|---|---|---|
| 沸騰ボタンの受付 | 100msec × 1 | `pot-230-11` (`pot-230-21` は「ブザーは鳴らさず」と明示) |
| 保温設定ボタンの受付 | 100msec × 1 | `pot-240-21` |
| エラー検出 | 30秒 | `pot-500-11` / `-21` / `-31` |

**現在の図はエラーからの1本しか引いていない** (`pot-230-11` / `pot-240-21` は未反映).
またブザーは 100msec / 30秒 と鳴り方が異なるので, 水位メータの `表示パターン` と同様に
`鳴動パターン` 属性を持たせるのが素直である.

さらに sheet3 にしかない鳴動が2件ある.

| 出典 | 内容 | sheet4 の状況 |
|---|---|---|
| sheet3 `B153` | ボタンが押されたらブザーを1回鳴動 | 解除ボタン `pot-250-21`・給湯ボタン `pot-260-11` には鳴動の記述が一切ない |
| sheet3 `B155` | **沸騰状態終了時, ブザーを3回鳴動** | `pot-312-11` に記述なし. **お湯が沸いたことを知らせる手段が sheet4 だけでは存在しない** |

### E. その他の未規定

- アイドル時に保温モードの ▼ を表示するかどうか (`pot-240-41` は表示位置だけを規定)
- コンセント挿入直後のインジケータセルの初期状態 (`pot-221-12` は蓋開時の全消灯のみ規定)
- 水量異常の「判断」は蓋センサ on から 3sec 経過時の一度だけ (`pot-280-11`/`-12`) だが,
  保温中に給湯で水位が下がった場合の再判定については `pot-320-31` の「全水位センサ off」
  しか規定がない

### F. 追加すべきシーンの候補

現在の4枚では以下の要求が主役として確認できない. 優先順に:

| 追加シーン | 確認できるようになる要求 |

| 満水異常 | `pot-280-11` (許容上限超え), `pot-280-31` (満水点滅 500ms点灯/200ms消灯), `pot-220-31` |

## レンダリング

```bash
# 文法検証 (フォント不要)
plantuml -charset UTF-8 -checkonly docs/analysis/*.puml

# PNG 生成
plantuml -charset UTF-8 -DPLANTUML_LIMIT_SIZE=32768 -tpng docs/analysis/*.puml
```

`-DPLANTUML_LIMIT_SIZE` は必須. 既定値 4096px では図が右端で切れる.
出力ファイル名は `.puml` のファイル名ではなく **`@startuml` の後ろの名前**で決まるので,
両者を一致させておくこと.

必要な環境:

- `plantuml` (1.2026.2 で確認), `java`, `graphviz` (`dot`)
- 日本語フォント `Noto Sans CJK JP` (各 `.puml` の `skinparam defaultFontName` で指定)
