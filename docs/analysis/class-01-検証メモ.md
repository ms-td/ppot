# クラス図によるオブジェクト図の検証メモ

`class-01-クラス図.puml` を起こす過程と, それを要求仕様と突き合わせた結果の記録.

## 位置づけと方法

クラス図は**成果物ではなく検証装置**として作った. 手順:

1. オブジェクト図4枚を主体にクラスを起こす (**仕様から新規にクラスを足さない**)
2. 属性が要求する一般化・統合を施す (正規化)
3. 要求仕様と突き合わせ, オブジェクト図に対する発見リストを作る

「正規化版を描くと問題がきれいに吸収されて見えなくなる」という懸念があるため,
**破綻の証拠として機械抽出した属性表を §I-1 に載せている**.

新設11クラスの内訳が重要である.

- **9個は「型として存在していたのに平坦なクラス名の下に隠れていた」もの**
  `満水センサ` `第n水位センサ` `蓋センサ` `サーミスタ` はすべて `: センサ`,
  `アイドル` `沸騰行為` `保温行為` `エラー` はすべて `: ポット状態`,
  `インジケータセル` は `: ランプ` だった
- **本当に新しい抽象は2個だけ** — `二値センサ` と `温度制御行為`

つまりオブジェクト図の「21クラス」は, **3つの平坦なクラス名の下に9つの異なる型を隠していた**.

## I. 構造の問題 (クラス図を起こす過程で判明)

### I-1. 平坦な型付けの破綻 — 機械抽出した証拠

4枚のオブジェクト図から「クラス名 → 属性 → その属性を持つ実体」を機械抽出した結果.
**同一クラスの実体間で属性が排他的**になっているものが3クラスある.

```
■ センサ (サーミスタ / 満水センサ / 第n水位センサ / 蓋センサ)
    検出値          … 二値の3つのみ
    検出水温        … サーミスタのみ
    測定範囲        … サーミスタのみ
    デフォルト値    … 満水センサ・第n水位センサのみ (蓋センサとサーミスタには無い)
    番号            … 第n水位センサのみ
    on継続時間      … 蓋センサのみ
  → 4実体が共有する属性は<b>ひとつも無い</b>。単一クラスとして成立していない

■ ランプ (沸騰 / 保温 / ロック / インジケータセル×4)
    点灯状態        … 全部
    番号・対応センサ … インジケータセルのみ
  → 共通属性はあるが, インジケータセルだけ余分な属性を持つ → 派生が正しい

■ ポット状態 (アイドル / 沸騰行為 / 保温行為 / エラー)
    21属性のうち4実体すべてが持つのは「状態名称」だけ
    制御方式・操作量M・制御周期 … アイドル/沸騰行為/保温行為のみ (エラーには無い)
  → 中間の抽象クラスが必要
```

**判定基準は「属性の同一性」**である. これにより:

| クラス | 扱い | 理由 |
|---|---|---|
| `ボタン` | 派生を作らない | 4実体の属性が同一 (押下状態 / 有効性) |
| `ランプ` | 1派生 (`インジケータセル`) | 3実体は同一属性, インジケータセルだけ追加属性 |
| `二値センサ` | 3派生 | 実体ごとに属性が異なる |

### I-2. 同じ事実の重複 (4件)

| 重複 | 残す側 | 根拠 |
|---|---|---|
| `保温行為.段階 = 保温中/給湯中` と `給湯状態.給湯中` | **`保温行為.段階`** | 状態遷移シート 6.4 が `保温中 ⇄ 給湯中` を保温行為の内部状態として描く |
| `ポット.検知しているエラー` / `エラー検出.エラー種別` / `エラー.エラー種別` (**三重**) | **`エラー.エラー種別`** | 現在状態が エラー のときの種別として持つのが自然. `ポット` 側は `現在状態` から導出 |
| `ロック状態.ロック状態` と `給湯口.ロック` | **`給湯口.ロック状態`** | `pot-250`「給湯口のロック/ロック解除機能を付ける」 |
| `保温モード設定.保温モード`・`目標温度` と `保温行為.保温モード`・`目標温度 Tg` | **`保温モード設定`** | 設定値はコンセント直後から存在し (`pot-240-11`), 保温行為中でなくても保持される |

### I-6. 機能パッケージと型階層の衝突

**これは今回いちばん構造的な発見である.**

オブジェクト図は sheet4 の要求グループに合わせて6つの機能パッケージに切っている.
ところが汎化階層は機能をまたぐ.

```
二値センサ (0) ──▷ 満水センサ (3) / 第n水位センサ (3) / 蓋センサ (2)
ポット状態 (0) ──▷ 温度制御行為 (0) ──▷ アイドル (4) / 沸騰行為 (4) / 保温行為 (4)
               └─▷ エラー (6)
ランプ (0)     ──▷ インジケータセル (3)
```

クラス図では汎化線が図の端から端まで伸び, 階層が追いにくい. 対処として階層の一覧を
note に併記したが, **機能で package を切ることの代償**として記録しておく.

これは以前「機能で package を切ると物理的な構成木が図をまたぐ」と分かったのと同じ現象が,
型の階層でも起きているということである.

### I-7. 値域の違反 — `ヒータ.動作状態`

クラス図の値域は `on / off` (瞬時値) だが, 図03 は次の値を入れている.

```
動作状態 = 制御周期内で on/off を繰り返し中 (制御周期の 14% を on) 【pot-400-11】
```

**属性値が値域から外れている.** `pot-400-11` は「ヒータを操作量の%数だけonし、それ以外はoffする」
なので, ヒータの瞬時値は `on / off` であって「14%をon」は**操作量Mの話**である.

→ 訂正案: `動作状態` は瞬時値 `on / off` のままとし, 図03 の「制御周期の14%をon」は
`保温行為.操作量M = 14%` で表す (すでにある). ヒータ側の記述は note に移す.

### I-8. `温度制御方式` をクラスにすべき (**最重要**)

sheet4 は `A158:温度制御方式` を**独立した要求グループ**として持つ.

| 要求ID | 内容 |
|---|---|
| `pot-400-11` | 制御方式共通. ヒータを操作量の%数だけonする. 操作量の%数は**制御周期の時間の%数** |
| `pot-400-21` | 目標温度ON/OFF方式. 目標温度≦温度でoff, >でon. 操作量は 100% / 0% |
| `pot-400-31` | PID制御方式. Kp / Ki / Kd と ⊿M の式 |
| `pot-400-41` | 温度制御テーブル方式 (参考) |

ところが現在は `温度制御行為.制御方式` という**属性1つに畳んでいる**. このため
Kp/Ki/Kd, ON/OFF規則, デューティ比の定義に置き場がない.

**決定的な証拠**: クラス図で `保温行為` が持つ3属性は, **いずれも `pot-400-31` を引用している**.

```
今回水温 T0 / 前回 T1 / 前々回 T2   【pot-400-31】
前回操作量 M1                        【pot-400-31】
⊿M = Kp(T1-T0) + Ki(Tg-T0) + Kd(2T1-T0-T2)  【pot-400-31】
```

`pot-400-31` は「温度制御方式」の要求であって `pot-320` (保温行為) ではない. つまり
**引用IDが所属クラスと食い違っており, これらは保温行為の属性ではなく PID制御方式の属性である**.

訂正案:

```
温度制御方式 (abstract)      制御周期 / 操作量M              【pot-400-11】
  ├─ 目標温度ON/OFF方式      目標温度≦温度→off(0%) / >→on(100%)  【pot-400-21】
  ├─ PID制御方式             Kp / Ki / Kd / T0,T1,T2 / M1 / ⊿M   【pot-400-31】
  └─ 温度制御テーブル方式    <<参考>> 操作量テーブル              【pot-400-41】

沸騰行為 ── 目標温度ON/OFF方式   【pot-310-21】
保温行為 ── PID制御方式          【pot-320-21】
```

これにより `pot-400-41` の未引用 (§II) も解消する.

### I-9. 3つのエラーは派生クラスにすべき

sheet4 は `D194:＜高温エラー＞` `D197:＜温度下がらずエラー＞` `D199:＜温度上がらずエラー＞` の
**3つの独立した見出し**を持ち, 検知条件も想定原因も異なる. 現在は `エラー.エラー種別` という
属性1つに畳んでいるため, 種別ごとの違いが隠れている.

### I-10. `エラー検出` の属性はエラー種別と1対1対応している

| `エラー検出` の属性 | 対応するエラー |
|---|---|
| `高温しきい値 = 110°C を超えた場合` | 高温エラー `pot-500-11` |
| `98°C超過継続時間 : しきい値 3分` | 温度下がらずエラー `pot-500-21` |
| `検出周期 = 1分` / `前回検出水温` / `温度上がらず判定` | 温度上がらずエラー `pot-500-31` |

つまり `エラー検出` は1クラスではなく**3つの判定を束ねたもの**である. §I-9 と合わせて
`高温エラー判定` / `温度下がらずエラー判定` / `温度上がらずエラー判定` の派生に分けるべき.

**注**: §I-7 は値域の照合で, §I-8〜I-10 は要求仕様との突き合わせで判明した.
§I-1〜I-6 (クラス図を起こす過程で判明したもの) とは発見の経路が違う.

## II. モデル要素が無いもの

仕様の要求ID 81件のうち, モデルがどこでも引用していないのは5件だった.

| 要求ID | 内容 | 欠けているモデル要素 |
|---|---|---|
| **`pot-221-11`** | 蓋センサが**1sec以上off**となったら温度制御行為を中止する | `蓋センサ.off継続時間` が無い. `on継続時間` (3sec) しかない |
| **`pot-221-12`** | 蓋開時にインジケータセル全てのランプを消灯する | `水位メータ.表示パターン` に「全消灯」の値が無い |
| **`pot-210-12`** | コンセントを抜くと, ポットは**蓋の開け閉め以外は何も機能しなくなる** | `ポット状態` に「未通電」が無い. 状態遷移シート 6.1 はコンセント接続から始まるので状態機械の外だが, 蓋だけは動くという要求は表現されていない |
| **`pot-400-41`** | 温度制御テーブル方式 (参考) | `制御方式` の値に無い. 参考扱いなので意図的な除外でよいが記録しておく |
| `pot-100-15` | 貯水部は断熱性の高いステンレス素材 | `貯水部` クラスはあるがIDを引用していない. **この材質が「要決着A」(`pot-500-21` の自然冷却中の誤検知) の原因**なので引用すべき |

加えて, **IDは引用しているが因果の置き場がない**ものがある.

`pot-221-13`「蓋を開けたらロックされていたらロック解除し, ロックランプを消灯する」は引用済みだが,
クラス図には「蓋開 → ロック解除 → ランプ消灯」という因果を置く場所がない. 値としては
`給湯口.ロック状態` と `ランプ.点灯状態` に置けるが, **因果は状態遷移図の管轄**である.

そして, IDは引用しているが**属性として持っていない**ものがある.

| 要求ID | 内容 | 欠けている属性 |
|---|---|---|
| `pot-230-11` `pot-240-21` `pot-250-21` | ボタンが **100msec以上**押されると | `ボタン.押下継続時間` が無い. `押下状態` (押下/非押下) だけ |
| `pot-500-11`/`-21`/`-31` | 30秒間ブザーを鳴らす | `ブザー.鳴動パターン` に文章で入っているだけ. `残り鳴動時間` は `エラー` にしかない |
| `pot-280-31`/`-41` | 500msec / 200msec の点滅周期 | `水位メータ.表示パターン` の値名に埋め込まれているだけで, 周期が属性になっていない |

## III. 過剰なもの

### III-1. 廃止したクラス (2件)

| クラス | 廃止理由 | 移し先 |
|---|---|---|
| `給湯状態` (属性: 給湯中 / 給湯不可の理由) | 「給湯中」は `保温行為.段階` と重複. 「給湯不可の理由」は導出 | `保温行為.段階` と `ポンプ.動作状態` |
| `ロック状態` (属性: ロック状態 / エラー時の操作可否) | 1属性のみ. `給湯口.ロック` と重複 | `給湯口.ロック状態` |

### III-2. 外す候補 (1件)

`水位判定` は正規化後の属性が `/水量区分` (導出) と `判定時点` だけになる. 判定条件は制約で書ける.

```
{満水 ⇔ 蓋センサ on から 3sec 経過時に 満水センサ on}      【pot-280-11】
{空   ⇔ 同時点で 全ての第n水位センサ が off}               【pot-280-12】
{適正 ⇔ 上のいずれでもない}
```

ただし `pot-280` は「ポット内の水量をインジケータで表示する」という独立した要求グループなので,
クラスとして残す判断もありうる. **今回は残して note を付けた**.

### III-3. 残すと判断したもの

| クラス | 理由 |
|---|---|
| `保温モード設定` | デフォルト値 (`pot-240-11`), ボタン操作 (`pot-240-21`), 表示 (`pot-240-41`), 保温行為への適用 (`pot-320-21`) があり独立した設定概念 |
| `エラー検出` | 検出周期・前回検出水温・98°C超過継続時間を持つ監視概念として有効. ただし `エラー種別` の重複は消した |
| `給水線` | 制御に関与しないが, `pot-110-19` が「満水センサの位置よりも若干下」と定め, これが「満水」の解釈の根拠になっている |
| `表示窓` | 実体は1つ (`温度/モード表示窓`) だけだが, ハードウェアが1つの窓なので分割しない (`pot-240-41`「温度/モード表示窓に」) |

## IV. 給湯まわりで決まらないこと (最重点)

オーナーの予想どおり, **給湯中のシーンがオブジェクト図に無いため, 給湯まわりが確定できない**.
具体的に3点ある.

### IV-1. 「給湯中」は状態か, ポンプ動作の別名か

`pot-260-11` の本文はこう書く.

> 以下の条件を全て満たすとき、給湯ボタンを押している間、ポンプを作動する(給湯する)。
> 一つでも条件を満たしていなければ給湯できない。
> ・ロック解除状態であること ・水量が適正であること ・蓋センサがonであること
> ・ヒータ用電源がonであること ・温度エラーを検知していないこと ・保温行為中であること

これだけ読むと「給湯中」は**ポンプ作動中の別名**に見える. 一方, 状態遷移シート 6.4
(保温行為状態遷移図) は `保温中 ─(給湯要求)→ 給湯中`, `給湯中 ─(給湯要求解除)→ 保温中` と描き,
**保温行為の内部状態**として扱っている.

どちらを正にするかで, `保温行為.段階` を持つのか `ポンプ.動作状態` から導出するのかが変わる.
**給湯中シーンが無いので検証できない.**

### IV-2. 開始条件と途中停止条件が一致しない

`pot-260-21` はこう書く.

> 給湯中に一つでも以下の条件になったとき、給湯ボタンを押している間でも、ポンプの動作を停止する
> (給湯を止める)。 ・水量が異常になる ・ヒータ用電源がoffになる ・温度エラーを検知する

開始条件は6つなのに, **停止条件は3つだけ**である. 抜けているのは
**蓋センサon / ロック解除状態 / 保温行為中** の3つ.

したがって「給湯中に蓋が開いた場合」は, `pot-221-11` により温度制御行為は中止されるが,
**ポンプ停止は `pot-260-21` から直接は言えない**. 開始条件を常時ガードとして読むのか,
途中停止は3条件だけなのかが決まらない.

これは安全性に関わる. 蓋を開けた状態で給湯が続くと解釈できてしまう.

### IV-3. ポンプ停止後も「給湯中」と呼ぶのか

`pot-230-21` は「保温行為中で**給湯中**の場合、沸騰ボタンを100msec以上押しても…遷移しない」と書き,
`pot-250-31` も「**給湯中**」を解除ボタン無効の条件にしている.

しかし `pot-260-21` でポンプが止まったあと, 給湯ボタンを押し続けている状態を「給湯中」と呼ぶのか,
`保温中` に戻るのかが未定義である. **「給湯中」の同一性が決まらない.**

→ **次に追加すべき検証シーンは「給湯中」が最優先**である.

## V. 複雑さの評価

「クラス図として複雑化するなら現状のオブジェクト図の構造が複雑なのかもしれない」という仮説の検証.

**結論: 構造そのものより表現の重複が主因.** ただし1点だけ構造的な問題がある.

### 複雑さの出所

| 出所 | 分類 | 具体 |
|---|---|---|
| 1属性だけの状態保持クラス | 表現 | `ロック状態` (廃止), `給湯状態` (廃止) |
| 導出値の属性化 | 表現 | `on検出センサ数`, `セル数`, `取付先`, `給湯不可の理由` |
| 同じ事実の別名保持 | 表現 | 重複4件 (§I-2) |
| 平坦な型付け | 表現 | `センサ` に4つの異なる型を詰めていた (§I-1) |
| 値域の違反 | 表現 | §I-7. `ヒータ.動作状態` に非瞬時値が入っていた |
| **機能パッケージと型階層の交差** | **構造** | §I-6. 機能で切ると汎化が図をまたぐ |
| **独立した概念を属性に畳んでいた** | **構造** | §I-8 `温度制御方式` / §I-9 エラー3種 / §I-10 エラー検出の3判定 |

表現の問題は正規化で解けた. クラス数は 21 → 30 に増えたが, これは**隠れていた型が表に出た**
結果であって複雑化ではない. オブジェクト図31オブジェクトという数自体は問題ではない.

**構造的な問題は2系統ある.**

1. **オブジェクト図由来** — §I-6 (機能パッケージと型階層の交差) と §I-7 (`ヒータ.動作状態` の
   値域違反). §I-6 は機能パッケージを選んだことの代償であり, 以前「機能で切ると物理的な構成木が
   図をまたぐ」と分かったのと同じ現象. 機能分割をやめる理由にはならないが, クラス図では
   階層一覧の note で補う必要がある.
2. **仕様との突き合わせで出た追加の構造候補** — §I-8 (`温度制御方式` のクラス化),
   §I-9 (エラーの派生クラス化), §I-10 (`エラー検出` の判定分割). いずれも
   **仕様が独立した見出しを持っている概念を属性1つに畳んでいた**という同型の問題である.
   §I-8 は引用IDと所属クラスの食い違いという形で機械的に検出できた.

つまり「オブジェクト図の構造が複雑」なのではなく, **仕様が独立の概念として立てているものを
属性に畳んでいたために, かえって置き場所を失っていた**というのが実態である.

## VII. 判断が分かれた点

### `温度制御行為` に `アイドル` を含めるか

**含める判断をした.** 根拠:

- sheet4 の B列大見出し `B100:＜温度制御行為＞` の配下に `A101:沸騰行為` `A125:保温行為`
  `A139:温度制御行為をしない(アイドル)` の3つが並ぶ. 次の大見出し `B157:＜温度制御方式＞` は
  row 157 なので, **アイドルは仕様上 ＜温度制御行為＞ の中にある**
- 3者は `制御方式` `操作量M` `制御周期` を共有する (`pot-330-21`「操作量を0%とする」)

Codex は「`pot-330` が『沸騰行為も保温行為もできないときは温度制御はしない』と書くので
アイドルを派生にするのは不自然」として除外を推した. 意味論としては妥当な指摘だが,
仕様の構成と属性の共有を優先した. **アイドルは「何もしない温度制御行為」という位置づけ**である.

**ただし §I-8 で `温度制御方式` をクラス化する場合は再検討が必要**. `制御周期` と `操作量M` が
`温度制御方式` 側に移ると, `温度制御行為` の共通属性が減り, アイドルを派生にする根拠が弱まる.
その場合は `アイドル` を `ポット状態` の直接の派生とし, `操作量M = 0%` を持つ
「温度制御停止」状態として扱う方が整理される可能性がある (Codex の再評価).

### `<<use>>` の読み方

クラス図の `..>` `<<use>>` は**分類子レベルで利用する関係**として読むべきで,
実行時の一回の値読み取りを直接表す線ではない. オブジェクト図で「説明線」が逸脱だったのは
インスタンス間の実行時参照に依存を流用していたからであり, クラス間なら本来の意味で使える.
