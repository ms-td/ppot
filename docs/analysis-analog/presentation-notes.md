## 3. 現在のクラス構成 (`分析-クラス指定/クラス`, 図「電子ポット」)

### 役割ごとのまとまり

**窓口: ポット** — 外からの出来事を受け、行為切替・給湯口・表示部などへ振り分ける。

| 呼び手 | ポットの操作 |
|---|---|
| 操作部 (利用者の要求。ボタンからの振り分けは操作部の責務) | `再沸騰要求()` (沸騰ボタン), `保温モード変更()` (保温設定), `給湯ロック変更()` (解除), `給湯要求()` / `給湯要求解除()` (給湯) |
| 蓋 (事実の通知) | `蓋が閉じた()`, `蓋が開いた()` |
| 水位計 (事実の通知) | `水量異常()` |
| 温度エラー監視 (事実の通知) | `温度エラー検知()` |

呼び手が 2 種類 (要求 / 事実) あるので操作の名前が不揃いに見えるが、設計モデルで呼び手ごとに
インタフェースを分ける (講師の予定) ための区切りそのもの、と説明できる。

**行為の切り替え: 行為切替** (旧名 ポット状態) — 仕様 6.1/6.2 の状態遷移
(アイドル中 / 沸騰行為中 / 保温行為中 / エラー中) を持ち、沸騰行為・保温行為を
「温度制御行為を 2 つ」(ロール名 沸騰 / 保温) として持つ。操作は 6.2 のイベントそのもの:
`沸騰要求()`, `沸騰処理完了()`, `温度制御停止()`, `エラー検知()`。
ほかに `保温行為中か()` と `現在水温読み出し()` (保温モード変更後の再沸騰判断用)。

**温度制御: 温度制御行為 {abstract} ← 沸騰行為 / 保温行為** — `開始()` / `停止()` (entry/exit 相当)、
`目標温度読み出し()`, `現在水温読み出し()`。サーミスタを読み、ヒータを動かし、温度エラー監視を
開始・停止し、表示部へ温度表示・ランプ・鳴動を指示する。外から見える形が同じなので、行為切替は
派生クラスを区別せずに扱える (リスコフの置換原則)。制御方式 (ON/OFF, PID) は各行為に埋め込み
(図のノート「制御方式は埋め込み」)。

**保温モード** — モード (高温/節約/ミルク) と温度。保温行為が `開始()` のときに
`保温温度読み出し()` で取りに行く。

**温度エラー監視 + 温度エラー判定 {abstract} ← 高温 / 温度上がらず / 温度下がらず** —
監視は判定 3 つを固定で持つ (ロール名 高温 / 温度上がらず / 温度下がらず)。
行為が `監視開始(対象)` で見たい判定を指定し、選ばれた判定はリセットされる。判定はサーミスタを
直接読む。

**入力**: 蓋 – 蓋センサ / 水位計 – 水位センサ (ロール名 第n位水位センサ [1..*] と 満水センサ [1]) /
操作部 – ボタン (ロール名 沸騰・保温設定・解除・給湯)

**出力**: 表示部 – ランプ (ロール名 沸騰・保温・ロック) / インジケータセル (第n位インジケータセル
[1..*]) / 温度表示 / モード表示 / ブザー。ヒータ、ヒータ用電源、給湯口 – ポンプ。

**給湯口** — ロックと給湯中を自分で管理する (状態 ロック解除中{待機中, 給湯中} / ロック中)。
`給湯開始()` / `給湯停止()` / `ロック変更()` は、できなければ断って成否を返す
(呼び手が先に確認しなくてよい)。`給湯中でないか()` は沸騰ボタンのガード用。

## 6. 設計判断とその理由 (話の種)

- **再沸騰 (保温モード変更後)**: 仕様シート3「100°C でなかった場合、一度沸騰させたあと…」を採用。
  モード変更そのものは状態を動かさず、水温を確かめて沸騰要求を出す。保温行為には必ずカルキ抜き直後
  (100°C) に入るので、その直後の変更では再沸騰しない (pot-312 の「電力の無駄を避ける」とも合う)。
  詳細は [CLAUDE.md](../../CLAUDE.md) の Known internal conflicts #2。
- **保温温度は取りに行く**: 講師版は保温モードから押し付ける形だったが、値の持ち主が 1 か所になり、
  「新しい温度は次に保温行為に入ったときから効く」が構造で表せるので変更。
- **給湯中は給湯口が持つ**: 保温行為の操作をポットへ移した結果。ポンプを動かす給湯口が給湯中を
  知るのが自然。代わりに「行為切替が保温行為中を抜けたら給湯も止まる」は自動ではなくなるので、
  ポットが水量異常・エラー時に給湯停止を指示する (pot-260-21)。
- **確かめてから頼む → 頼んで成否を返してもらう** (Tell, Don't Ask): 給湯開始・給湯停止・ロック変更。
  ロックや給湯中の規則を給湯口だけが知っていればよくなり、確認の手順が減る。
- **事実の通知と要求の区別**: 蓋・水位計・監視は事実 (蓋が閉じた, 水量異常…)、操作部は利用者の要求
  (再沸騰要求…)。業務への読み替えはポット、ボタンの振り分けは操作部。
- **判定のリセットは監視開始時**: 行為が監視開始で対象の判定を指定し、選ばれた判定が初めからやり直す。
  pot-500-21 の 3 分の計測が保温行為に入るたびに始め直しになる。
- **状態遷移図の状態名 = 列挙型の値**: 講師の指示。状態遷移図とクラス図が名前でつながる。
- **水位センサのロール名**: 第n位水位センサ [1..*] と 満水センサ [1] に分け、「うち 1 つは必ず
  満水センサ」をノートではなく構造で表した。センサの数に意味を持たせないという仕様の意図 (pot-280 の
  説明) と、満水センサだけは別機能という例外の両方が図に出る。
- **仕様の解釈で講師に確認したこと** ([memo.md](memo.md)):
  - A. pot-500-21 が自然冷却中に成立するか → 成立しないこととする

## 7. KPT の材料 (候補。採否と言い回しは発表者が決める)

**Keep 候補**
- シナリオをテキストで先に書き、仕様 ID を手順に付けてから図にした (図と仕様の対応が追える)
- シナリオ (テキスト) → コミュニケーション図 → シーケンス図 と、同じ流れを段階的に図にした
- 繰り返しの作業 (シナリオの往復、図の照合、シーケンス図の生成) を道具で機械化し、モデルの判断に
  時間を使えた
- 仕様の曖昧な点は質問として書き出して講師に確認した (memo.md)
- 指摘を受けるたびに、シナリオ・コミュニケーション図・シーケンス図まで一貫して直した

**Problem 候補**
- 講師から構成を指定され、自分たちの設計から大きく組み替えることになった (粒度の差)
- 名前が中身とずれた: ポット状態 (派生元のメタな名前のまま、役割が変わった)、水位
- 確かめてから頼む形が多く、手順が長くなった (後に成否を返す形へ)
- 状態遷移図と列挙型・属性の名前が揃っていなかった (指摘で揃えた)
- 図から外した要素がモデルに残り、整合を崩しやすかった

**Try 候補**
- 設計モデルで、呼び手ごとのインタフェース分離 (講師の予定とも一致)
- 責務の境界 (誰が確かめ、誰が決めるか) を早めに文章で決めてから図にする
- 名前は役割が変わったら早めに見直す
- 状態を持つクラスは、状態遷移図・列挙型・属性を最初から対で作る

## 8. 資料づくりに使えるもの

- 図は EA から画像として書き出す (クラス図「電子ポット」、状態遷移図、コミュニケーション図、
  シーケンス図)。パッケージは `分析-クラス指定` の下: `クラス/` (クラス図と状態遷移図)、
  `コミュニケーション-シナリオ/<場面>/`、`シーケンス図/<短い名前>/`。
- 旧構成との比較: `分析` パッケージ (クラス図「クラス図」、状態のサブクラス + 温度制御器)。
- テキスト: シナリオ ([communication-scenarios-クラス指定.md](communication-scenarios-クラス指定.md))、
  仕様 (`docs/spec/要求仕様.txt` ほか。ID で grep できる)、仕様の状態遷移図 `docs/spec/images/image14.png`。
- スクリプト (使い方は [CLAUDE.md](../../CLAUDE.md)):
  - `python scripts/ea_scenarios.py -m 分析-クラス指定 export` — EA のシナリオを md へ
  - `python scripts/ea_sequence_from_comm.py -m 分析-クラス指定` — コミュニケーション図からシーケンス図
  - `scripts/ea_copy.py` — パッケージのコピー (分析 → 分析-クラス指定 の取り込みに使った)
- EA の `.qeax` は SQLite。書き込む前に EA を閉じ、バックアップを取ること (CLAUDE.md)。
