# KPT 発表原稿

KPT 研修で得られた知見について, Keep を3つ, Problem と Try は2組ずつです. まず Keep からお話しします.

## Keep 1: 仕様が束になっていること

1つ目は, 仕様がある程度まとまっていることです. 今回の研修で, 作業上一番やりやすいと感じたのは, 正直この点でした.
これくらいの仕様の束があるなら, 設計のやりようがでてくると感じました. 実際の製品でも, これくらいの要件が出揃っていると, 設計はかなりやりやすくなるのではないかと思います.

## Keep 2: EA でアクター越しにシナリオを共有すること

2つ目と3つ目は少し似ていますが, まず2つ目は, EA でアクターを介してシナリオを共有することです.
今回の研修では, コミュニケーション図で, 最初に User アクターを置き, そこへシナリオや事前条件などを設定しました. そのあとシーケンス図でも, 同じように User を置いて, 同じシナリオを設定しています.
こうしておくと, コミュニケーション図で作成した内容が, ほぼ同じオブジェクトやメッセージとしてシーケンス図にも現れます. 図としての見え方は違っても, 同じ内容を追える点がかなりよいと感じました.

## Keep 3: シナリオをテキストファイルで先書きしたこと

3つ目は, シナリオをテキストファイルで先に書いたことです. これは私が独自にやっていた方法です.
EA の中でシナリオを管理すると, 事前条件や事後条件を変更するたびにリンクを貼り直す必要があり, 少しやりづらさがありました. また, シナリオを見ながら別の図を確認したい場合も, 図を開かないと内容を見にくいと感じました.
そのため, シナリオはまずテキストで書き, そこから図に反映する形にしました. 最後に User のノートにあるリンクを書き換えるだけで済むので, EA の中だけで書き換えて図を作り直すより, 余計な手間を減らせたと思います.

## Problem 1: 初期にEAで作られたオブジェクト図がなおざり

ここから Problem と Try です. Problem, Try の順でお話しします.

最初の Problem は, 初期に EA で作ったオブジェクト図が, 途中からあまり活用されなくなったことです. 
クラス図はインスタンスとしてコミュニケーション図やシーケンス図とつながっていますし, コミュニケーション図やシーケンス図はUser アクターでつながっています.
一方で, 最初に作られたオブジェクト図は比較的独立した状態で, ほかの成果物との関連があまりありませんでした. クラス図が整ってきたあたりから, オブジェクト図に触れることがほとんどなくなりました.

## Try 1: EAに限られない形式でも良いのではないだろうか

今回のように研修で EA を使うことが決まっている場合は EA で作成しますが, 実際の業務で, 最初の考えを起こすことを目的に使い捨てなオブジェクト図でよければ, 別段 EA に限らず, 描きやすいツールでまとめ始めても十分ではないかと思いました.

## Problem 2: 想定されているだろうクラスとずれた

2つ目の Problem は, 想定されているクラスと, こちらで作ったクラスが途中でずれたことです.
作成中にも細かな確認はしていたつもりですが, この先に何を作っていくのか, 今作っている構造を先で何に使うのかが見えなく, ところどころ納得しきれないと感じる局面がありました.

## Try 2: 何を先で使のかを質しておく

こちらからできることとしては, 「この内容を先で何に使うのか」を早めに質しておくことくらいかなと考えております.

### サブ: シラバス等で仕様書外の情報貰えるとよりよくなるだろう

ただ, 加えて, これは講師側への提案ですが, 研修のシラバスや資料などで, 研修の先行きやEAの利用機能など仕様書の外にある情報を少しでも共有してもらえると,
例えば, 「設計フェーズのどこでこの部分の詳細化を行う」といった情報を先にもらえると, そんなずれは 事前に かなり減らせるのではないかと思います.
また, この研修は設計分析から設計まで通して, 全体で6か月ほど想定されている長丁場な研修です. そして, UML の基礎知識や EA の基本的な使い方も受講者側に必要になります. そこにシラバスがあれば, 「今, 分析のどのフェーズで作成した部分について作業しているのか」などで振り返りやすくなりますし, どこかで実業務からの要請で一旦離れてしまっても, 研修の再開や復帰がしやすくなると考えられます.
